## 三、发现

### P1 = 1（阻断关闭）

**P1-1：正式长稳不稳定，Codex 声称的"85 cycle 全过"不能复现。**

- 现象：独立跑 `pnpm run harness:arh3.3.3`（formal），3 轮完整 semantic replay 通过（`semanticResultDigest=sha256:c78fc2cab…` 三轮一致、52/52），但长稳第 26 个轻量 cycle、约 15 分钟处失败。
- 证据：`qa-reports/arh3.3.3-runs/2026-08-16T05-59-54-223Z/failure.json`
  - `errorCode=arh333.lightweight_stability_cycle_failed`，`phase=stability`，`completedStabilityCycleCount=26`；
  - `typedErrorCodes=["arh333.stability_central_failed"]`；
  - `failureLocations` 指向 `Cgf2b32…#executesArh333LightweightTakeoverAndResourceClosure` → `awaitFailpointBlocked` → `awaitCondition`。
- 定性：`awaitFailpointBlocked` 是 failpoint 阻塞检测的时序窗口，与 CTR-P3-001 的"backend did not enter the blocking execution"签名同类，**不是生产 fencing/lease 缺陷**（`model_gateway.fencing_epoch_conflict` 是设计内预期错误码，Cgf2b32 F6 断言其出现）。但轻量 takeover 测试**继承了**该时序敏感点，长稳反复运行仍会偶发超时。
- 复跑：单独复跑 `executesArh333LightweightTakeoverAndResourceClosure` 3 次全过（12–13 s/次），证明是偶发时序，非稳定失败。偶发恰恰否定"稳定性"结论本身。
- 影响：ARH-3.3.3 的核心阶段关闭证据（30 分钟长稳稳定性）不可靠，**阻断关闭**。Codex 声称"CTR-P3-001 未被归入或修复"与"85 cycle 全过"之间存在矛盾——它既未修复 failpoint 时序，又未在长稳中消除该敏感点。

### P3 = 1

**P3-1：`resource-cleanup.test.ts` 偶发失败（Document Worker 既有测试，非 ARH-3.3.3 引入）。**

- 现象：首次 `CI=true pnpm run check` 时 `services/document-worker/tests/harness/resource-cleanup.test.ts:149` 失败，`expect(exitCode).toBe(0)` 收到 `null`（SIGTERM 后 worker 未在 200ms 内优雅退出，被默认 signal 终止）。
- 复跑：单独复跑 3 次全过；`CI=true pnpm run check` 复跑 166/1170 全过。
- 定性：Document Worker 既有测试用 200ms 固定延迟发 SIGTERM，高负载下偶发不够；与 ARH-3.3.3 无关，但暴露 Workspace 测试套件的时序脆弱性。

2. 修复后从零重跑 `pnpm run harness:arh3.3.3`，证明长稳能**稳定**通过（非运气），并提交独立 QA 复跑。
