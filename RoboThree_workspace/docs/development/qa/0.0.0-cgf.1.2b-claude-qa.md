## 12 项独立 QA 逐条验证

### 1. Node 64/440 + Central 53/0/0 双门禁

✅ **PASS** — 三门禁独立重跑全量通过。Docker Testcontainers 与 Embedded PostgreSQL 均实际执行，0 skipped。

### 2. TypeScript consumer 与 canonical Enterprise Gateway 同 corpus

`packages/contracts/tests/enterprise-configuration-consumer.test.ts`：直接运行 canonical Enterprise Gateway `v1alpha1` Fixture corpus。Consumer 不包含 candidate、SQLite path、Runtime Handle、Token 或 credential 字段。

✅ **PASS** — TS consumer 与 canonical corpus 同源，strict unknown/local field 拒绝。

### 3. Snapshot/Package/file digest、byte/path、kind partition、exact ref → 顺序失败关闭

`ConfigurationValidator` 按固定顺序验证：
- 兼容性 → bounded Snapshot bytes → strict Schema → canonical digest → descriptor partition → exact reference → Package path/file/package digest

`PackageMaterializer` 要求 Agent/Skill exact 引用完整闭包，生成绑定四因素 scope + Snapshot facts 的 `candidateKey`。

新增 `services/core/tests/enterprise-configuration-validation.test.ts` 覆盖校验失败路径。

✅ **PASS** — 校验链按固定顺序失败关闭，错误只返回 typed code 和安全摘要。

### 4. candidateKey 绑定四因素 + exact Snapshot，materializationDigest 顺序无关

`candidateKey` = SHA-256（`enterpriseId` + `userId` + `deviceId` + `clientInstanceId` + `snapshotId` + `snapshotRevision` + `snapshotDigest`）。四因素 scope 精确绑定。

`materializationDigest`：按稳定 key 排序后计算，输入顺序不影响最终 digest。

✅ **PASS** — candidateKey 绑定四因素 + exact Snapshot，materializationDigest 顺序无关。

### 5. InMemory/SQLite 同一 Conformance：begin/package/seal/activate replay、conflict、scope 隔离、CAS

`enterprise-configuration-persistence.conformance.test.ts`：两个 variant（InMemory + SQLite）运行同一 Conformance，覆盖：

| 场景 | 预期 |
| --- | --- |
| 同输入 begin → replay | 同结果，`replayed: true` |
| 同 revision 不同 digest → conflict | `configuration.persistence_conflict` |
| 不完整 seal（缺 package） | `configuration.candidate_incomplete` |
| 不同 scope 隔离 | `configuration.scope_mismatch` |
| CAS stale writer（错误 expectedActiveRevision） | `configuration.activation_conflict` |
| unsealed discard | 成功移除 |
| diagnostics | candidate/sealed/unsealed/materialized bytes 正确 |

✅ **PASS** — InMemory/SQLite 同一 Conformance，replay/conflict/scope/CAS/discard 全覆盖。

### 6. SQLite 独立数据库 + 独立 migration namespace

SQLite schema（`enterprise-config-V1`，`enterprise-configuration-migrations.ts`）：

| 特性 | 实现 |
| --- | --- |
| 数据库文件 | `enterprise-configuration.sqlite`（独立于 Task/Session SQLite） |
| Migration 表 | `enterprise_configuration_schema_migrations`（独立 namespace） |
| Migration 命名 | `enterprise-config-V1`（非 Task/Session 的 V1） |
| Checksum preflight | SHA-256 of `enterprise-config-V1\n<sql>` |
| Foreign key | `PRAGMA foreign_keys = ON` |
| Integrity preflight | 表/索引/checksum 完整校验 |

6 个业务表：`candidates`、`candidate_packages`、`scope_pointers`、`activations`、`status_events` + migration 管理表。Scope 隔离通过 `UNIQUE(enterprise_id, user_id, device_id, client_instance_id)` 约束。

Central V1～V5 migration MD5 全部不变，无 V6。

✅ **PASS** — 独立数据库、独立连接、独立 migration namespace。Task/Session migration 和 Central V1～V5 未改写。

### 7. active pointer 提交后响应丢失只产生一次 activation/event，重试 replay

Storage Activation 在单事务内写 active/previous pointer、activation record 和 status event。Commit 后响应丢失 → 重试 → `activateSealedCandidate` 调用 CAS（`expectedActiveRevision` 匹配已激活 revision）→ 同 candidate 重试返回 replay。

SQLite 集成测试覆盖 close/reopen 场景：reopen 后 active 完整可读。

✅ **PASS** — activation 单事务原子写入，重试 replay。

### 8. close/reopen、较新 migration、缺表/integrity/foreign-key 失败关闭

- close/reopen：active configuration 完整保留 ✅
- 较新 migration（`schema_version > LATEST`）：启动失败关闭 ✅
- 缺表/索引：integrity preflight 检测并失败关闭 ✅
- Foreign key 违规：SQLite `PRAGMA foreign_keys = ON` 强制执行 ✅

✅ **PASS** — close/reopen 保持完整，异常 schema 失败关闭。

### 9. 无网络调用进入 SQLite transaction，无自动 GC，无持久化 pendingRuntimeActivation

- `ConfigurationActivationCoordinator` 协调 stage/seal/activate，网络下载明确留在事务外 ✅

- `pendingRuntimeActivation` 不进入任何数据库表/列——Activation Status 从 `storageActiveRevision`/`runtimeActiveRevision` pointer 和 status events 派生 ✅

✅ **PASS** — 网络在事务外、无 GC、无持久 pending bool。
