## 0. 结论摘要

R2D-3.1 已冻结 Runtime Selection v1alpha3 与 coordination v1alpha4，R2D-3.2 已交付单一
`AgentResourceDecisionPlanner`、可信资源交集、code-owned `agent.general` 与 fixture 隔离。R2D-3.3 只负责把这些
既有事实接入第一次 `SubmitTurn` 的 durable acceptance 流程。

本批不新建第二套 coordination，不要求跨 Conversation、Task、coordination 三个 Repository 的全局物理事务。
它冻结的产品级原子语义是：

1. `accepted` 时已经形成唯一、可严格恢复的 exact acceptance plan；
2. `message_appended` 只推进既有状态机，不重新选择任何资源；
3. Task、Model/Tool locks、Runtime Selection v1alpha3、Authorization、ReasoningModeLock、Task SubmitTurn Binding
   与 Task Instruction Binding 在同一个 Task Persistence transaction 中形成唯一 durable winner；
4. 只有该 winner 可 strict load 且 coordination 已进入 `task_committed` 后，才允许进入 Provider/Invocation 路径；
5. response loss、restart、transaction replay 和 terminal replay 均复用原 plan、原 locks、原 selection、原
   ReasoningModeLock 与原 instruction identity，不重新读取 current authority；
6. production gate 在本批结束时继续关闭。

R2D-3.3 不修改已冻结的 coordination v1alpha4 Contract。由于 v1alpha4 `resourcePlan` 只包含 digest 与 ID，无法单独
重建完整 Task bundle，本批新增两个 **Core-private persistence envelope**：

- coordination `record_json`：保存 `v1alpha4 record + DurableAcceptancePlanV1`；
- Task `binding_json`：保存 `TaskSubmitTurnBinding + TaskInstructionBindingV1`。

二者都复用既有 JSON 列、既有表和既有事务，不新增 migration 27，不扩宽 public/private Contract subpath，不把
Secret、正文或本机 material 写入 durable plan。

## 3. Core-private Durable Acceptance Envelope

### 3.1 为什么必须有 envelope

`SubmitTurnResourcePlanV1Alpha4` 是安全摘要面，只能证明计划身份，不能承载完整 capability lock snapshots、完整
Runtime Selection v1alpha3 或 authorization material。若恢复阶段只持有该 Contract，唯一可行的重建方式是重新读取
Agent、entitlement、Preference、Registry 或 Tool policy；这违反本批的 exact recovery 边界。

因此本批在 persistence adapter 内引入 Core-private envelope，而不是改写 v1alpha4 Contract：

```text
PersistedR2D3CoordinationEnvelopeV1
  schemaVersion = "r2d3_coordination_envelope_v1"
  record          = SubmitTurnRecordV1Alpha4
  acceptedPlan    = DurableR2D3AcceptancePlanV1
  envelopeDigest = sha256(domain + canonical material)
```

legacy v1alpha1～v1alpha3 coordination 继续以原 raw record JSON 读取；新 envelope 通过最外层 discriminator 单次
dispatch。未知 discriminator、缺 plan、重复字段、digest 不匹配、indexed column 与 record 漂移均 fail-closed，禁止
“先按 envelope 读失败再按 legacy 猜”。

### 3.2 DurableR2D3AcceptancePlanV1 字段

计划至少包含以下 exact material：

- `submitTurnCommandId / clientTurnId / internalSessionId / internalTaskId`；
- `userMessageId / checkpointId / runtimeSelectionId`；
- request digest、selection request digest、accepted client binding digest；
- exact Agent ref 与 `managementClass`；
- entitlement snapshot digest 与 AgentResourceDecision full content-free record；
- exact Model lock、ordered Tool locks、ReasoningModeLock；
- exact Runtime Selection v1alpha3；
- authorization selection 与 execution selection identity；
- exact Task head/checkpoint 初始 material；
- exact public `TaskSubmitTurnBinding`；
- exact `TaskInstructionBindingV1`；
- `acceptanceReceiptIdentity`，固定等于 `submitTurnCommandId`，作为业务 Receipt identity；
- 独立预分配的 `preallocatedDeliveryId`，仅作为 transport delivery identity；
- `acceptedAt` 单次时间事实；
- `planDigest`。

不允许包含：

- user message text、System Prompt/Agent/Skill/Knowledge 正文；
- entitlement 全量未选资源清单；
- Credential、Token、Secret、owner raw identity、endpoint、workspace path；
- Provider raw request、reasoning raw mapping、Tool payload/result；
- mutable current pointer 或 Renderer 自报 authority。

### 3.3 canonical digest

固定 domain separator：

```text
robothree.r2d3-durable-acceptance-plan.v1\n
```

`planDigest` 只覆盖 plan material，不覆盖其自身，也不覆盖 coordination record/status，避免循环摘要。固定构造顺序：

1. 分配所有 stable IDs 与单次 `acceptedAt`；
2. 产生 exact decision、locks、selection、authorization；
3. 产生 `TaskSubmitTurnBinding.bundleDigest`；
4. 用 exact selection + bundle digest 派生 `TaskInstructionBindingV1`；
5. 计算 `planDigest`；
6. 创建 v1alpha4 `resourcePlan`，其中
   `durableAcceptanceRevision = planDigest`，其他 digest/ID 与 plan 精确交叉绑定；
7. 创建 envelope digest。

`record.resourcePlan.acceptanceReceiptIdentity` 必须精确等于 `submitTurnCommandId`。现有
`SubmitTurnReceipt.submitTurnCommandId` 是业务 Receipt 的稳定身份；`preallocatedDeliveryId` 只允许填入 eventual
`DesktopDeliveryRecord.deliveryId`。两者必须分别持久化、分别重放、分别校验，transport Delivery identity 不进入
business Receipt 校验路径。本批不新增公共 Receipt ID 字段，也不把任一 identity 当作用户已经收到 response 的证明。

### 3.4 envelope 生命周期

- `prepareAccepted`：在现有 coordination transaction 中插入 v1alpha4 record + plan envelope；
- `transition`：只更新 record/status/timestamps，必须原样保留 acceptedPlan，重算 envelope digest；
- `complete`：completed record、Receipt、独立 `preallocatedDeliveryId` 对应 delivery 原子写入，acceptedPlan 继续
  保留，并基于 completed record 重算 envelope digest；
- `failTerminal`：保留 acceptedPlan，基于 failed_terminal record 重算 envelope digest，不把 failure 写成可重新选择；
- accepted/message_appended/task_committed/completed/failed_terminal 任一 record 字段变化而 envelope digest 未同步变化，
  必须视为 corrupt；
- `load/listRecoverable`：返回严格验证后的 record + plan view；legacy raw record 仍走旧路径；
- same commandId/clientTurn replay：plan digest 必须 exact 相同，否则 typed conflict。

## 4. 首次接受阶段的固定读取与执行次数

### 4.1 唯一 first-accept 路径

仅在“没有 existing command、没有 existing clientTurn、没有 durable accepted envelope”时允许进入 first-accept：

1. strict parse SubmitTurn v1alpha3；
2. 查询 commandId 与 clientTurnId，各一次；命中则走 exact replay/conflict；
3. resolve requested exact Agent 或 code-owned `agent.general`，**恰好一次**；
4. interpret Agent restriction，**恰好一次**；
5. `TaskResourceEntitlementSource.loadExact()`，**恰好一次**；
6. capture exact Registry revision 与 ordered entries，**恰好一次**；
7. capture Workspace/authorization safe facts，各**恰好一次**；
8. user Model Preference：仅未 explicit 选择时读取，**至多一次**；explicit 路径必须为 0；
9. `TaskToolCandidatePolicy.resolveExact()`，**恰好一次**；
10. `AgentResourceDecisionPlanner.plan()`，**恰好一次**；
11. rejected/unavailable/drift 在 Conversation intent、coordination、Task、Receipt durable count 全 0 时返回；
12. materialize exact locks、selection v1alpha3、authorization 与 Task/Instruction bindings；
13. prepare exact Conversation message intent；
14. `prepareAcceptedEnvelope()` 保存唯一 accepted winner；
15. 进入既有状态机推进。

步骤 10 后禁止重新读取 current Agent、entitlement、Preference、Registry ordering 或 Tool policy改变 winner。

### 4.2 Conversation intent 与 coordination 的诚实边界

本批不新建跨 Repository transaction。Conversation message intent 与 coordination accepted record 仍是两个局部原子事实：

- message intent 可在 accepted 前 prepared；若进程在二者之间终止，该 intent 是不可见、不可执行的惰性事实；
- 相同 command/clientTurn 重试必须用 exact identity/digest 收敛，不创建第二条可见 Message；
- 不得把孤立 intent 解释为 Task accepted；
- 不得用 catch 后删除模拟跨 Repository rollback；
- R2D-4 lifecycle harness 负责真实进程窗口的最终 closure，本批用 deterministic fault injection/conformance 固定语义。

这不是“所有 Repository 同一物理事务”，也不得在报告中如此宣称。

## 5. 唯一 coordination 状态机

### 5.1 状态与允许动作

| 状态 | 唯一允许动作 | 禁止动作 |
| --- | --- | --- |
| `accepted` | 从 envelope 取原 message identity/material，append/replay exact message | 重新 Agent/entitlement/Preference/Registry/Tool policy/Planner |
| `message_appended` | 从 envelope 提交/replay exact R2D3 Task bundle | 重新 materialize locks/selection，resolve Provider |
| `task_committed` | strict load bundle，验证全绑定，构造 Receipt/delivery | 重选资源，写第二套 Task，启动未验证 bundle |
| `completed` | exact Receipt/delivery replay；首次且仅一次启动既有 Agent Loop | 新 Task/Message/locks/selection/Provider replay |
| `failed_terminal` | exact failure Receipt replay | fallback 到 legacy 或 default Agent/Model |

不增加新的 coordination status，不增加第二张表，不把 `task_committed` 改名或挪义。

### 5.2 v1alpha4 cutover

- v1alpha1～v1alpha3 existing records 按既有 readable union 与恢复语义继续读取；
- 只有 gate-on、依赖完整且新 SubmitTurn v1alpha3 first-accept 才创建 v1alpha4 envelope；
- 已创建 v1alpha4 record 不允许 fallback 到 v1alpha3；
- unknown/corrupt envelope 不允许按 legacy raw record 重试解析；
- gate 从 true 变 false 后，既有 v1alpha4 recoverable record 必须按 exact durable plan完成或安全失败，不能遗弃；
- gate=false 不创建新 v1alpha4 record，也不改变既有 production route 行为。

## 6. R2D3 Task Bundle 原子提交

### 6.1 新 Core-private Port 类型

新增 `R2D3SubmitTurnTaskBundle` 与 `PersistedR2D3SubmitTurnTaskBundle`，包含：

- Task head + initial checkpoint；
- ordered Model/Tool `TaskCapabilityLock[]`；
- Runtime Selection v1alpha3（其内含独立 ReasoningModeLock）；
- TaskAuthorizationSelection + TaskExecutionSelectionIdentity；
- public `TaskSubmitTurnBinding`；
- Core-private `TaskInstructionBindingV1`。

`TaskInstructionBindingV1` 不属于 R2D-3.3 新 schema。必须直接复用
`services/core/src/application/instruction-bundle-domain.ts` 已有的：

```text
TaskInstructionBindingV1Schema
deriveTaskInstructionBindingV1FromValidatedSelection()
validateTaskInstructionBindingV1()
```

原始未验证 selection 如需进入通用入口，可调用既有 `deriveTaskInstructionBindingV1()`；R2D-3.3 Task bundle validator
已经持有 validated selection，因此固定使用 `deriveTaskInstructionBindingV1FromValidatedSelection()`，禁止新增
`createTaskInstructionBindingV1` 或另一套等价 helper。

新增明确方法，例如：

```text
commitR2D3SubmitTurnTaskBundle()
loadR2D3SubmitTurnTaskBundle()
```

禁止通过顺序调用旧 `commitTaskCapabilityLock / commitTaskRuntimeSelection / commitAuthorization...` 模拟聚合提交。

### 6.2 binding_json 私有 envelope

既有 `task_submit_turn_bindings.binding_json` 对 R2D3 新记录保存：

```text
PersistedR2D3TaskBundleBindingEnvelopeV1
  schemaVersion = "r2d3_task_bundle_binding_v1"
  submitTurnBinding
  taskInstructionBinding
  envelopeDigest
```

indexed columns 继续与 `submitTurnBinding` 精确一致。legacy row 继续保存原 raw `TaskSubmitTurnBinding`。读取时按明确
discriminator 单次 dispatch；损坏 R2D3 envelope 不 fallback legacy。

### 6.3 SQLite transaction 与 InMemory 等价原子提交

SQLite 与 InMemory 必须执行同一 validator/conformance：

1. strict validate acceptance plan；
2. 重算 Model/Tool lock digests 与 ordered identities；
3. strict validate Runtime Selection v1alpha3 与 selection digest；
4. 验证 ReasoningModeLock exact 绑定 Task + Model lock，且不混入 capability lock IDs；
5. strict validate authorization selection/execution，并绑定 selection digest；
6. 重算 public TaskSubmitTurnBinding bundle digest；
7. 从 validated selection + bundle digest 重新派生 TaskInstructionBindingV1；
8. 与 plan 中 planned instruction binding exact 比较；
9. SQLite 在一个 database transaction 内插入 Task、Checkpoint、locks、selection、authorization、binding envelope；
10. commit 后 strict reload 全 bundle；
11. reload material 与 accepted plan 七类 digest/identity 全一致才返回成功。

SQLite 任一步失败必须整体 rollback。InMemory 不得因“内存可信”跳过 digest、排序、duplicate、schema 或交叉绑定
校验，也不得在 validation 后依次修改多个 live Map。InMemory 固定采用：

1. 从 current state clone 完整 staged state；
2. 在 staged state 中完成全部插入、strict reload 与交叉绑定复验；
3. 任一 fault/throw 只丢弃 staged state，current state 保持逐字不变；
4. 全部验证完成后，以单一 `this.#state = stagedState` pointer swap 作为唯一 commit point；
5. swap 后不得再执行可失败解析或逐 Map 补写。

编码时如现有多个 private Map 无法由单一 state object 持有，必须先做本 Adapter 内部最小 state 聚合；禁止把
“全部可失败解析尽量提前”当成等价原子证明。

### 6.4 Task Instruction Binding 的含义

`TaskInstructionBindingV1` 是从 durable selection + bundle digest 确定性派生的既有 Core-private fact。本批复用
`deriveTaskInstructionBindingV1FromValidatedSelection()` 生成、用 `validateTaskInstructionBindingV1()` 验证，并通过
SQLite transaction / InMemory staged-state commit 写入 binding envelope，使它与 Task bundle 同时成为 durable
winner；不新增 schema、helper、独立表或 migration。load 时必须重新派生并验证，仅“JSON 中存在一个 digest”不能
构成证明。

## 7. `task_committed` Provider 前 barrier

### 7.1 硬边界

在 coordination 成功 transition 到 `task_committed` 前，以下计数必须全部为 0：

1. Provider resolver；
2. Credential resolver；
3. DNS；
4. socket；
5. TLS；
6. HTTP request body / Central gateway dispatch；
7. Model Invocation Link prepare/insert；
8. Agent Loop start；
9. Usage projection；
10. Compaction/model invocation。

现有实现从 `completed` 后启动 Agent Loop，本批保持这一更强顺序：

```text
Task bundle commit
  -> strict reload
  -> coordination task_committed
  -> complete Receipt/delivery
  -> coordination completed
  -> Agent Loop start
  -> Provider resolve / Invocation
```

不得为了“更快首字”把 Provider resolve 提前到 Task transaction、`message_appended` 或 `task_committed` transition 之前。

### 7.2 证据要求

- architecture test 扫描 coordinator/loop/provider 调用图，不能仅硬编码 `false`；
- test-only diagnostic Ports 为上述十类计数提供真实 observation；
- fault point 必须覆盖 Task transaction before/after commit、coordination transition before/after commit；
- `task_committed` 前任一 fault 后十类计数仍为 0；
- `completed` terminal replay 的 Task/Message/lock/selection/Provider/Invocation 新建计数全 0；
- 资源数量来自真实 diagnostic snapshot，禁止 `?? 0`、默认 0 或父进程相信 child 报告。

## 8. Recovery、response loss 与并发收敛

### 8.1 accepted/message_appended recovery

恢复只允许读取：

- strict coordination envelope；
- exact Conversation intent/message；
- exact Task bundle（若 transaction 已有 durable winner）。

恢复必须满足：

```text
Agent current load count = 0
Entitlement load count = 0
Preference load count = 0
Registry current/order load count = 0
Tool policy load count = 0
Planner run count = 0
new ID allocation count = 0
```

任何 envelope、message、bundle digest/identity drift 均 typed fail-closed，不允许重新 plan、fallback legacy、改用
`agent.general`、切 current Model 或删除不可用资源后继续。

### 8.2 task_committed/completed recovery

- Task commit 已成功但 transition response loss：一次 strict load exact bundle；exact match 后仅推进原 record；
- transition 已成功但 complete response loss：业务 Receipt 继续使用 exact `submitTurnCommandId`，Delivery 继续使用
  独立 `preallocatedDeliveryId`；
- completed response loss：分别验证 Receipt/Delivery identity 后返回原 persisted Receipt，不再次启动 Agent Loop；
- loop_started 标记 response loss：沿用既有 at-least-once 诚实语义，不把它伪装 exactly-once；
- Provider/network failure：只影响既有 Task run，不修改 accepted plan 或资源 winner；
- retry、Tool 后续轮、Compaction、restart 继续使用原 Runtime Selection、ReasoningModeLock、Instruction Binding、
  R2D-1 Dynamic Request Facts 与 migration 25 durable deadline。

### 8.3 并发规则

- same commandId + exact material：single durable winner，loser exact replay；
- same commandId + different material：`r2d.acceptance_conflict`；
- same clientTurnId + different commandId：typed conflict；
- duplicate Task/binding/lock identities：不得猜 winner；只在 exact envelope + exact bundle 全匹配时 replay；
- transaction loser 不 sleep、不轮询、不自动重新 Planner；rollback 后最多一次 strict reload；
- late callback/runtime restart 不得覆盖已锁定 termination/result。

## 9. Agent 与 fixture 隔离

### 9.1 新 Task

- 缺显式 Agent 时，R2D path 只能使用 code-owned `BuiltInGeneralAgentSource` 的 exact `agent.general` v1alpha2；
- `agent.general` 必须保持 `system_builtin`、四类 unrestricted、无 default Model；

## 11. Typed errors 与安全边界

| code | 触发事实 | 安全摘要 |
| --- | --- | --- |
| `r2d.acceptance_plan_invalid` | envelope schema/digest/交叉绑定损坏 | 任务运行配置无法验证 |
| `r2d.acceptance_plan_unavailable` | v1alpha4 record 缺 exact plan | 任务运行配置暂不可用 |
| `r2d.acceptance_conflict` | command/clientTurn 已绑定不同 material | 该请求与已接受任务不一致 |
| `r2d.task_bundle_conflict` | existing bundle identity/material 不一致 | 任务配置与已保存记录不一致 |
| `r2d.task_bundle_invalid` | selection/lock/auth/binding reload 损坏 | 任务配置无法验证 |
| `r2d.instruction_binding_invalid` | instruction binding 缺失或重算不匹配 | 任务指令配置无法验证 |
| `r2d.activation_incomplete` | gate=true 但 production 依赖不完整 | 新任务运行能力尚未就绪 |
| `r2d.provider_barrier_violation` | task_committed 前发生上游副作用 | 任务启动顺序无法验证 |

错误输出不得包含 resource ID、digest、Agent/Skill/Knowledge 正文、owner、Credential、Endpoint、SQL、Zod path、stack
或文件路径。`unavailable` 不得伪装成 `denied/unsupported`；persistence failure 不得返回 accepted/success。

## 16. 停手条件
